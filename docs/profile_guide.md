## 1. Назначение и область применения

### 1.1. Назначение

Настоящий документ устанавливает требования к профилю интероперабельности для обмена перечнями разрешённых радиоэлектронной аппаратуры (РЭА) и электронной компонентной базы (ЭКБ) между информационными системами участников кооперации.

### 1.2. Область применения

Профиль применяется при:
- Обмене данными о разрешённых перечнях ЭКБ/РЭА между организациями
- Проверке соответствия изделий разрешённым перечням
- Управлении допустимыми заменами компонентов
- Интеграции данных между системами управления конструкторскими данными

### 1.3. Уровни интероперабельности

Профиль обеспечивает два уровня интероперабельности (ГОСТ Р 77.403):

| Уровень | Описание | Реализация |
|---------|----------|------------|
| **Семантический** | Единая модель данных перечней ЭКБ/РЭА | XSD-схема профиля, словари, классификаторы |
| **Технический** | Форматы обмена данными | XML + XSD 1.1, Schematron |

**Примечание:** Организационный уровень интероперабельности не входит в область применения данного профиля и регулируется отдельными соглашениями между участниками обмена.

## 6. Степени интероперабельности

### 6.1. Уровни соответствия

| Уровень | Название | Критерии | Минимальная степень |
|---------|----------|----------|---------------------|
| **A** | Базовый | • Валидация XSD пройдена<br>• Все обязательные атрибуты заполнены | 0.50 |
| **B** | Расширенный | • Уровень A пройден<br>• ≥70% рекомендуемых атрибутов заполнено<br>• Schematron валидация пройдена | 0.75 |
| **C** | Полный | • Уровень B пройден<br>• ≥90% рекомендуемых атрибутов заполнено<br>• Все Schematron правила пройдены<br>• Маппинг 2.525 ↔ 2.058 валиден | 0.95 |

### 6.2. Формула расчёта

```
Степень = (M_filled / M_total) × 0.5 + (R_filled / R_total) × 0.3 + (S_passed / S_total) × 0.2

Где:
  M_filled — заполненные обязательные атрибуты
  M_total — всего обязательных атрибутов
  R_filled — заполненные рекомендуемые атрибуты
  R_total — всего рекомендуемых атрибутов
  S_passed — пройденные правила Schematron
  S_total — всего правил Schematron
```

### 6.3. Пример расчёта

| Параметр | Значение |
|----------|----------|
| Обязательные атрибуты (заполнено/всего) | 7/7 = 1.00 |
| Рекомендуемые атрибуты (заполнено/всего) | 4/6 = 0.67 |
| Правила Schematron (пройдено/всего) | 10/12 = 0.83 |
| **Степень интероперабельности** | **(1.00 × 0.5) + (0.67 × 0.3) + (0.83 × 0.2) = 0.87** |
| **Уровень** | **B (Расширенный)** |

## 7. Правила расширения профиля

### 7.1. Принцип неизменности ядра

Ядро профиля (обязательные элементы) **НЕ МОЖЕТ** быть изменено расширениями.

### 7.2. Допустимые расширения

#### 7.2.1. Наследование через xs:extension

```xml
<!-- Допустимо -->
<xs:complexType name="ExtendedComponentType">
  <xs:complexContent>
    <xs:extension base="eskd-ekb:AllowedComponentItemType">
      <xs:sequence>
        <xs:element name="industrySpecific" minOccurs="0"/>
      </xs:sequence>
    </xs:extension>
  </xs:complexContent>
</xs:complexType>
```

#### 7.2.2. Дополнительные атрибуты через xs:any

```xml
<xs:complexType name="ProfileExtensionType">
  <xs:sequence>
    <xs:any namespace="##other" processContents="lax" 
            minOccurs="0" maxOccurs="unbounded"/>
  </xs:sequence>
</xs:complexType>
```

#### 7.2.3. Отдельный namespace для расширений

```
Ядро:     http://gost.ru/eskd/profile/ekb/2024
Расширение: http://gost.ru/eskd/profile/ekb/2024/extension/{industry}
```

### 7.3. Недопустимые действия

| Действие | Статус | Обоснование |
|----------|--------|-------------|
| Изменение обязательности атрибутов ядра | ❌ Запрещено | Нарушает контракт профиля |
| Удаление элементов ядра | ❌ Запрещено | Нарушает семантику профиля |
| Изменение типов данных ядра | ❌ Запрещено | Нарушает валидацию |
| Переопределение элементов через restriction | ❌ Запрещено | Нарушает наследование |

### 7.4. Регистрация расширений

1. Создать отдельный XSD-файл расширения
2. Импортировать ядро профиля
3. Использовать уникальный namespace
4. Документировать правила применения

### Приложение D. Поддержка жизненного цикла согласования (ГОСТ 2.124-2014)

#### D.1. Маршрут согласования (ApprovalRoute)

Для отслеживания статуса согласования каждой позиции перечня используется элемент `approvalHistory`. Он позволяет зафиксировать этапы прохождения позиции от проекта до утверждения в соответствии с требованиями ГОСТ 2.124-2014 (пункт 4.2 «Порядок согласования»).

**Структура элемента:**
- `stage`: этап согласования (`draft`, `under_review`, `approved`, `rejected`, `voided`).
- `date`: дата перехода в текущий этап (формат ГГГГ-ММ-ДД).
- `responsiblePerson`: ФИО или идентификатор ответственного лица.
- `comment`: комментарий согласующего (опционально).

**Пример использования:**
```xml
<ekb:approvalHistory>
    <ekb:stage>under_review</ekb:stage>
    <ekb:date>2024-01-20</ekb:date>
    <ekb:responsiblePerson>Иванов И.И.</ekb:responsiblePerson>
    <ekb:comment>Требуется подтверждение производителя о сроках поставки</ekb:comment>
</ekb:approvalHistory>
```

Элемент `approvalHistory` может повторяться多次 для отражения полной истории согласования позиции.

#### D.2. Данные об импортных компонентах (ImportedComponentData)

Для компонентов иностранного производства предусмотрен блок `importData`, содержащий сведения о сертификатах и разрешениях на применение в соответствии с ГОСТ 2.124-2014 (пункт 5.1 «Учёт покупных изделий иностранного производства»).

**Структура элемента:**
- `certificateNumber`: номер сертификата соответствия или разрешения.
- `certificateDate`: дата выдачи документа.
- `issuingAuthority`: наименование органа, выдавшего документ.
- `technicalDocumentation`: ссылка на техническую документацию изготовителя (опционально).

**Пример использования:**
```xml
<ekb:importData>
    <ekb:certificateNumber>RU.C.12345.АБВ.001</ekb:certificateNumber>
    <ekb:certificateDate>2023-05-15</ekb:certificateDate>
    <ekb:issuingAuthority>Федеральное агентство по техническому регулированию</ekb:issuingAuthority>
    <ekb:technicalDocumentation>https://example.com/datasheet.pdf</ekb:technicalDocumentation>
</ekb:importData>
```

Оба элемента (`approvalHistory` и `importData`) являются опциональными (`minOccurs="0"`) для обеспечения обратной совместимости с документами, созданными до введения данных требований.

### Приложение E. Автоматизированная проверка соответствия (ГОСТ 2.053-2023, ГОСТ 2.111-2013)

#### E.1. Модуль проверки соответствия

Модуль `eskd_compliance_check.xsd` предоставляет механизм детальной поэлементной проверки состава изделия на соответствие разрешённому перечню. Результатом является отчёт `ComplianceReport`.

**Нормативная база:**
- ГОСТ 2.053-2023, пункт 7.2.1 — проверка состава электронной структуры изделия.
- ГОСТ 2.111-2013, пункт 6.3 — оформление результатов нормоконтроля.
- ГОСТ 2.111-2013, пункт 5.1.2 — ответственность за результаты проверки.

#### E.2. Структура отчёта (ComplianceReportType)

Отчёт содержит общую информацию о проверке и детализацию по каждому компоненту.

**Основные поля:**
- `reportId`: уникальный идентификатор отчёта (обязательно).
- `productRef`: ссылка на проверяемое изделие или ЭСК (обязательно).
- `allowedListRef`: ссылка на перечень, по которому проводилась проверка (обязательно).
- `verificationDate`: дата выполнения проверки (обязательно).
- `overallStatus`: итоговый статус проверки (`full_compliance`, `partial_compliance`, `non_compliant`, `not_verified`).
- `checks`: последовательность результатов проверки отдельных компонентов (минимум 1).
- `verifier`: ссылка на организацию или лицо, выполнившее проверку (опционально).
- `remarks`: общие замечания по результатам проверки (опционально).

#### E.3. Статусы проверки отдельного компонента (ComplianceCheckType)

Для каждого компонента указывается статус проверки:
- `passed`: компонент соответствует перечню (найден, все параметры совпадают, ограничений нет).
- `failed`: компонент не найден в перечне или запрещён к применению.
- `warning`: компонент требует уточнения (устаревшая позиция, ограничения применения, условно разрешён).

**Пример фрагмента отчёта:**
```xml
<eskd-cc:compliance_report xmlns:eskd-cc="http://gost.ru/eskd/compliance/2024">
    <eskd-cc:reportId>НК-2024-001</eskd-cc:reportId>
    <eskd-cc:productRef ref="#PROD-001"/>
    <eskd-cc:allowedListRef ref="#LIST-001"/>
    <eskd-cc:verificationDate>2024-01-15</eskd-cc:verificationDate>
    <eskd-cc:overallStatus>partial_compliance</eskd-cc:overallStatus>
```

### Приложение F. Классификация конструкторских документов (ГОСТ 2.102-2023)

#### F.1. Коды видов документов

Модуль `eskd_document_classification.xsd` вводит классификатор `DocumentKindCodeEnum` в соответствии с таблицей 1 ГОСТ 2.102-2023.

**Поддерживаемые коды:**

| Код | Наименование | Описание |
|-----|--------------|----------|
| `СП` | Спецификация | Текстовый КД, определяющий состав сборочной единицы (ГОСТ 2.102-2023, п. 5.3.1) |
| `ЭСК` | Электронная конструктивная структура изделия | Электронный КД, определяющий состав изделия (ГОСТ 2.053-2023, п. 5.1) |
| `ВП` | Ведомость покупных изделий | Перечень покупных изделий, применяемых в изделии (ГОСТ 2.102-2023, п. 5.3.4) |
| `ВР` | Ведомость разрешения применения покупных изделий | Документ, утверждающий разрешённые покупные изделия (ГОСТ 2.124-2014, п. 4.3) |
| `ПЭ3` | Перечень элементов | Документ для схем, перечисляющий элементы (ГОСТ 2.102-2023, п. 5.3.8) |
| `ТУ` | Технические условия | Требования к изделию, не отражённые в других КД (ГОСТ 2.102-2023, п. 5.3.2) |
| `СБ` | Сборочный чертеж | Чертёж, показывающий соединение частей изделия |
| `ЧД` | Чертеж детали | Чертёж отдельной детали |
| `ПМ` | Программа и методика испытаний | Документ, устанавливающий порядок испытаний |
| `Д` | Документ (общий случай) | Общий тип для иных видов документов |

Полный перечень доступен в типе `DocumentKindCodeEnum` модуля `eskd_document_classification.xsd`.

#### F.2. Связь перечня с документами

В типе `AllowedComponentListType` предусмотрены ссылки на связанные документы:

- `purchasedItemsListRef` (IDREF, опционально): ссылка на документ типа **ВП** (Ведомость покупных изделий), из которого были отобраны компоненты для перечня.
- `permissionListRef` (IDREF, опционально): ссылка на документ типа **ВР** (Ведомость разрешения применения), утверждающий данный перечень.

В типе `AllowedComponentItemType` предусмотрена ссылка:
- `permissionDocumentRef` (IDREF, опционально): ссылка на позицию в документе типа **ВР**, если разрешение требуется для конкретной позиции.

**Пример связи:**
```xml
<ekb:AllowedComponentList id="LIST-001">
    <ekb:listId>ПЛ-2024-001</ekb:listId>
    <ekb:listName>Перечень разрешённой ЭКБ на 2024 год</ekb:listName>
    <ekb:documentKindCode>ВР</ekb:documentKindCode>
    <ekb:purchasedItemsListRef ref="VP-ABVG.123456.000-ВП"/>
    <ekb:permissionListRef ref="VR-ABVG.123456.000-ВР"/>
    <!-- ... элементы перечня ... -->
</ekb:AllowedComponentList>
```

*Соответствие: ГОСТ 2.102-2023, табл. 1; п. 5.3.4 (Ведомость покупных изделий), п. 5.3.5 (Ведомость разрешения применения); ГОСТ 2.124-2014, п. 4.3.*

#### F.3. Поддержка ЭСК как альтернативы спецификации

В соответствии с ГОСТ 2.053-2023 (пункт 5.1) и ГОСТ 2.102-2023 (пункт 5.2.1.1), электронная конструктивная структура изделия (`ЭСК`) может выполнять функцию основного конструкторского документа наравне со спецификацией (`СП`).

В элементах `productRef` (в `ComplianceReportType` и других типах) допускается ссылка как на объект типа `eskd_product` (из ГОСТ Р 2.525-2024), так и на объект электронной конструктивной структуры (`ElectronicStructure`).

Для обеспечения гибкости определён абстрактный тип `StructureDocumentType`, имеющий подтипы:
- `Specification` (для документов типа `СП`).
- `ElectronicStructure` (для документов типа `ЭСК`).

Это позволяет использовать единый интерфейс ссылки независимо от вида документа, представляющего структуру изделия.
