## Cценарии использования (use-case)

Предлагаемые сценарии расширяют базовые примеры из документации и ориентированы на практическое внедрение в инженерно-производственные контуры.

### 1. Валидация спецификаций и нормоконтроль на этапах проектирования и кооперации
**Контекст применения:**  
Инженер-конструктор формирует спецификацию изделия в САПР, интегрированной с системой управления данными (УДИ/PLM). 
Процесс охватывает как внутрикорпоративный нормоконтроль, так и сквозную проверку в многоуровневой кооперационной цепочке.

**Участники процесса:**  
Инженер-конструктор, система УДИ/PLM, отдел нормоконтроля, субподрядчики (2–3 уровень кооперации).

**Последовательность операций:**
1. Система генерирует экземпляр `ComplianceAssertion` для изделия, устанавливая ссылку на актуальный `AllowedComponentList`.
2. Запускается автоматизированная валидация пакета данных с использованием схемы XSD 1.1 и правил Schematron.
3. Рассчитывается степень интероперабельности `I` по формуле: `I = (M × 0.5) + (R × 0.3) + (S × 0.2)`.
4. При достижении порога `I ≥ 0.75` (уровень B) формируется протокол соответствия.
5. **Внутриорганизационный контур:** протокол маршрутизируется в отдел нормоконтроля для утверждения.  
   **Межорганизационный контур:** при `I < 0.75` экспорт пакета блокируется, генерируется реестр расхождений для согласования с головным исполнителем.

**Правила валидации и контроля:**
- Наличие и типизация всех обязательных атрибутов компонентов.
- Контроль статуса допуска: `approvalStatus ≠ prohibited`.
- Проверка целостности ссылок на нормативные документы (ГОСТ Р 2.525-2024, ГОСТ Р 2.058-2023).
- Соблюдение пороговых значений интероперабельности в зависимости от контура обмена.

**Ожидаемый результат:**  
Снижение риска применения неразрешенной ЭКБ/РЭА на этапе проектирования, автоматизация процедур нормоконтроля, предотвращение передачи невалидных данных по цепочке кооперации.

### 2. Управление заменами и импортозамещением в кооперационной цепочке
**Контекст применения:**  
Головной исполнитель и субподрядчики обмениваются данными о допустимых заменах иностранных компонентов на отечественные аналоги в условиях изменения статусов доступности (санкционные ограничения, EOL/NRND).

**Участники процесса:**  
Головной исполнитель, субподрядчики, уполномоченный куратор импортозамещения, интегрированные PLM-системы участников.

**Последовательность операций:**
1. Головной исполнитель публикует или актуализирует `ReplacementGroup` с указанием приоритизированных аналогов (атрибут `priority`, где `1` — предпочтительный).
2. Субподрядчики импортируют обновленный профиль в локальные УДИ, используя `eskd_binding.xsd` для семантического маппинга справочных ссылок.
3. Система автоматически проверяет совместимость версий (`profileVersion`) и наличие расширенных атрибутов уровня B (`manufacturer`, `qualificationStatus`).
4. Интегрированные PLM-системы пересчитывают допустимые аналоги, обновляют статусы применения и уведомляют инженеров о необходимости корректировки КД.
5. При снижении степени интероперабельности ниже установленного порога формируется отчет о несоответствиях для процедур согласования.

**Правила валидации и контроля:**
- Строгое соответствие версий профилей (`profileVersion`).
- Валидация структуры `ReplacementGroup` и корректности значений `priority`.
- Проверка полноты атрибутов уровня B для аналогов.
- Контроль семантической целостности при маппинге через модуль привязки.

**Ожидаемый результат:**  
Стандартизированный межорганизационный обмен данными без потерь семантики, оперативное управление импортозамещением в реальном времени, минимизация ручных корректировок конструкторской документации.

### 3. Интеграция с государственными и отраслевыми реестрами
**Контекст применения:**  
Автоматизированное сопоставление внутренних справочников ЭКБ/РЭА предприятия с внешними регуляторными базами данных (реестр Минпромторга, базы ФАУ «РСТ», отраслевые перечни разрешенной продукции).

**Участники процесса:**  
Интеграционный шлюз предприятия, внешние информационные системы регуляторов, ответственный за ведение НСИ.

**Последовательность операций:**
1. Извлечение данных из внутренних справочников предприятия.
2. Применение `eskd_binding.xsd` для маппинга внутренних идентификаторов на коды внешних реестров.
3. Трансформация данных в канонический XML-формат профиля.
4. Валидация структуры и расчет степени интероперабельности.
5. Передача пакета данных во внешние системы в соответствии с регламентами обмена (организационный и транспортный уровни регулируются отдельными соглашениями).

**Правила валидации и контроля:**
- Целостность перекрестных ссылок между внутренними и внешними идентификаторами.
- Обязательное заполнение полей, требуемых регуляторными реестрами.
- Соответствие бизнес-правилам Schematron для модуля НСИ.

**Ожидаемый результат:**  
Обеспечение семантической согласованности с государственными реестрами, автоматизация формирования отчетности по импортозамещению, исключение ошибок ручного сопоставления номенклатуры.

### 4. Формализованный приемочный контроль опытных образцов
**Контекст применения:**  
Передача изделия на квалификационные или приемочные испытания. Испытательные центры требуют машиночитаемого подтверждения комплектации образца утвержденной ЭКБ/РЭА.

**Участники процесса:**  
Разработчик/изготовитель, испытательный центр, система управления испытаниями.

**Последовательность операций:**
1. Формирование пакета данных уровня C (`I ≥ 0.95`) для опытного образца.
2. Передача пакета в контур испытательного центра.
3. Автоматизированная проверка комплектации: сверка фактического состава с утвержденной спецификацией, контроль `qualificationStatus`, валидация правил Schematron.
4. Генерация машиночитаемого протокола допуска к испытаниям с фиксацией базовой конфигурации.

**Правила валидации и контроля:**
- Достижение уровня интероперабельности C (порог `0.95`).
- Полнота заполнения рекомендуемых атрибутов не менее `90%`.
- Проверка временных меток: `effectiveDate ≤ verificationDate`.
- Отсутствие компонентов со статусом `prohibited` или `restricted`.

**Ожидаемый результат:**  
Исключение ручной сверки спецификаций, ускорение процедуры допуска к испытаниям, формирование объективной и верифицируемой конфигурационной базы образца.

### 5. Миграция и синхронизация данных при замене PLM/ERP-платформ
**Контекст применения:**  
Переход предприятия на новую систему управления данными или интеграция разнородных корпоративных платформ (например, отечественная PLM + legacy ERP). Профиль применяется в качестве эталонной модели обмена.

**Участники процесса:**  
Администраторы НСИ, интеграционные разработчики, исходная и целевая информационные системы.

**Последовательность операций:**
1. Экспорт данных об ЭКБ/РЭА из исходной системы в промежуточное представление.
2. Трансформация данных в XML-структуру профиля согласно правилам маппинга.
3. Валидация через XSD 1.1 и Schematron для подтверждения сохранности семантики атрибутов и статусов допуска.
4. Импорт валидированного пакета в целевую систему.
5. Фиксация метрик интероперабельности и журнала трансформационных ошибок.

**Правила валидации и контроля:**
- Структурное соответствие `eskd_core.xsd` и модулям профиля.
- Полнота переноса атрибутов и сохранение ссылочной целостности.
- Контроль версионности (`profileVersion`) и совместимости каталога профилей.

**Ожидаемый результат:**  
Бесшовная миграция данных без потери семантики, стандартизация интеграционного взаимодействия разнородных систем, снижение трудозатрат на разработку адаптеров.

### 6. Аудит соответствия при сертификации изделия
**Контекст применения:**  
Орган по сертификации проводит проверку конструкторской и сопроводительной документации на соответствие требованиям по применению разрешенной ЭКБ/РЭА.

**Участники процесса:**  
Заявитель (разработчик/изготовитель), орган по сертификации, автоматизированный валидатор.

**Последовательность операций:**
1. Заявитель предоставляет пакет данных в формате профиля с заявленным уровнем интероперабельности C.
2. Валидатор органа по сертификации выполняет полную проверку: XSD 1.1 + компилированные правила Schematron.
3. Контролируются бизнес-правила, полнота рекомендуемых атрибутов (`≥90%`), корректность маппинга между модулями ГОСТ Р 2.525-2024 и ГОСТ Р 2.058-2023.
4. Формируется машиночитаемый протокол аудита, содержащий расчетную степень интероперабельности, перечень замечаний и вердикт о соответствии.

**Правила валидации и контроля:**
- Строгое соответствие уровню C (`I ≥ 0.95`).
- 100% прохождение правил Schematron, включая временные и статусные ограничения.
- Верификация перекрестных ссылок между модулями 2.525 и 2.058.
- Наличие электронной подписи пакета данных (реализуется на транспортном уровне).

**Ожидаемый результат:**  
Автоматизация процедур сертификационного контроля, снижение субъективности аудиторских проверок, сокращение цикла сертификации за счет машиночитаемых протоколов.
